# Challenge 2: Correlate and Investigate with KQL

### Estimated Duration: 1.5 Hours

## Scenario

Zava Corporation's SOC queue contains many seeded incidents that look important at first glance. Most are noise, but one incident represents a real multi-signal compromise path: suspicious VM access activity followed by Azure network security group activity. Your job is to separate noise from signal, prove the true-positive incident with KQL evidence, and leave a clear investigation trail for the response engineer who will automate containment in the next challenge.

## Overview

In this challenge, you will hunt across Microsoft Sentinel data in the Microsoft Defender portal and the Sentinel workspace. You will use KQL to compare incidents, alerts, seeded evidence, endpoint events, and Azure control-plane activity. You will then investigate the incident created by **ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change**, preserve your findings as either a saved Sentinel/Log Analytics saved search or hunting query with display name prefix **ZAVA-Hunt-TruePositive**, or as a Microsoft Sentinel Hunting bookmark with that same prefix, and document the incident with the exact tag and comment marker required for validation.

**SecurityEvent** is supporting endpoint-context evidence in this challenge. It depends on the Windows Security Events via AMA/DCR work completed in Challenge 1 and on the fresh benign endpoint activity generated by the staged VM helper script. Your true-positive determination should rest on the seeded true-positive records plus **SecurityIncident**, **SecurityAlert**, and **AzureActivity** correlation; use **SecurityEvent** to enrich and validate the endpoint context, not as the only proof that the seeded true-positive incident is real.

## Task 1: Establish the Investigation Scope

In this task, you will identify the candidate incidents and understand how Sentinel records incident updates.

1. Work from the unified incident queue in the Microsoft Defender portal. Review the seeded incidents created before the lab and look for titles, alert names, related entities, and activity timelines that suggest more than a single noisy event.

2. Prioritize the incident associated with the analytics rule **ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change**. Do not close or delete noisy incidents during this challenge; you will tune noise later.

3. Open the investigation or incident details experience for the candidate incident and record these values in your notes:

   1. Incident number.
   2. Incident title.
   3. Severity and status.
   4. First activity time and last activity time.
   5. Affected host, account, source IP, and Azure resource entities.
   6. Related alert names and MITRE ATT&CK tactics, if present.

4. Run the following KQL to list the latest state of incidents. The **SecurityIncident** table records incident creation and updates, so use **arg_max** to keep only the latest row per incident number.

   ```kusto
   SecurityIncident
   | where TimeGenerated > ago(7d)
   | summarize arg_max(LastModifiedTime, *) by IncidentNumber
   | extend AlertCount = array_length(todynamic(AlertIds))
   | extend TagText = tostring(Labels)
   | project
       IncidentNumber,
       Title,
       Severity,
       Status,
       CreatedTime,
       FirstActivityTime,
       LastActivityTime,
       AlertCount,
       TagText,
       RelatedAnalyticRuleIds,
       IncidentUrl
   | order by Severity asc, LastActivityTime desc
   ```

5. Run the following KQL to isolate the true-positive incident candidate by rule name. If your result set is empty, widen the time range to 14 days before assuming the incident is missing.

   ```kusto
   let trueRule = "ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change";
   SecurityIncident
   | where TimeGenerated > ago(14d)
   | summarize arg_max(LastModifiedTime, *) by IncidentNumber
   | where Title has trueRule
       or Description has trueRule
       or tostring(RelatedAnalyticRuleIds) has trueRule
       or tostring(AlertIds) has trueRule
   | project
       IncidentNumber,
       Title,
       Severity,
       Status,
       CreatedTime,
       FirstActivityTime,
       LastActivityTime,
       AlertIds,
       Labels,
       Comments,
       IncidentUrl
   ```

## Task 2: Correlate Incidents and Alerts

In this task, you will connect the incident record to the alert evidence that caused it.

1. Query **SecurityAlert** for the seeded true-positive rule. Sentinel analytics rules generate security alerts, and those alerts are stored in the **SecurityAlert** table with fields such as **AlertName**, **DisplayName**, **SystemAlertId**, **Entities**, **Tactics**, **Techniques**, and **ExtendedProperties**.

   ```kusto
   let trueRule = "ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change";
   SecurityAlert
   | where TimeGenerated > ago(14d)
   | where AlertName == trueRule or DisplayName == trueRule
   | extend AlertEntities = parse_json(Entities)
   | project
       TimeGenerated,
       SystemAlertId,
       AlertName,
       DisplayName,
       AlertSeverity,
       CompromisedEntity,
       Tactics,
       Techniques,
       AlertEntities,
       ExtendedProperties
   | order by TimeGenerated desc
   ```

2. Join the latest incident state to related alerts. This confirms whether the incident and alerts agree on the same storyline.

   ```kusto
   let trueRule = "ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change";
   let Incidents =
       SecurityIncident
       | where TimeGenerated > ago(14d)
       | summarize arg_max(LastModifiedTime, *) by IncidentNumber
       | mv-expand AlertId = todynamic(AlertIds)
       | extend AlertId = tostring(AlertId)
       | where Title has trueRule
           or Description has trueRule
           or tostring(RelatedAnalyticRuleIds) has trueRule
           or tostring(AlertIds) has trueRule;
   Incidents
   | join kind=leftouter (
       SecurityAlert
       | where TimeGenerated > ago(14d)
       | where AlertName == trueRule or DisplayName == trueRule
       | project
           SystemAlertId,
           AlertName,
           DisplayName,
           AlertSeverity,
           Tactics,
           Techniques,
           Entities,
           ExtendedProperties,
           AlertTime = TimeGenerated
   ) on $left.AlertId == $right.SystemAlertId
   | project
       IncidentNumber,
       Title,
       Severity,
       Status,
       AlertName,
       DisplayName,
       AlertSeverity,
       Tactics,
       Techniques,
       AlertTime,
       Entities,
       ExtendedProperties
   | order by AlertTime desc
   ```

3. Compare the true-positive alert against noisy seeded alerts. Your goal is to prove that the true-positive case has stronger correlation, higher-impact entities, or a more suspicious sequence than the noisy incidents.

   ```kusto
   SecurityAlert
   | where TimeGenerated > ago(14d)
   | where AlertName startswith "ZAVA-"
   | summarize
       AlertCount = count(),
       FirstSeen = min(TimeGenerated),
       LastSeen = max(TimeGenerated),
       EntitiesSeen = make_set(CompromisedEntity, 20),
       TacticsSeen = make_set(Tactics, 20)
       by AlertName, AlertSeverity
   | order by AlertSeverity asc, AlertCount desc
   ```

4. Update your notes with why **ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change** is more credible than the noisy seeded rules. Include the alert name, affected entity, and the supporting incident number.

## Task 3: Hunt Across Seeded, Endpoint, and Azure Activity Evidence

In this task, you will hunt across at least three tables. Your final evidence must include three or more of the following: **SecurityIncident**, **SecurityAlert**, **ZavaSOCSeed_CL**, **SecurityEvent**, and **AzureActivity**. Treat **SecurityEvent** as supporting endpoint-context evidence that is available only if Challenge 1 AMA/DCR ingestion is working and fresh helper-generated VM events have landed. The true-positive finding is determined primarily by the seeded true-positive records and their correlation with **SecurityIncident**, **SecurityAlert**, and **AzureActivity**.

1. Query **ZavaSOCSeed_CL** for the seeded true-positive storyline. The seed table contains lab-specific fields that make the challenge deterministic while still requiring analyst judgment. These fields are normalized from both legacy type-suffixed custom log columns and unsuffixed variants so the query works across supported ingestion shapes.

   ```kusto
   ZavaSOCSeed_CL
   | where TimeGenerated > ago(14d)
   | extend
       ZavaCaseId = tostring(column_ifexists("ZavaCaseId_s", column_ifexists("ZavaCaseId", ""))),
       ScenarioType = tostring(column_ifexists("ScenarioType_s", column_ifexists("ScenarioType", ""))),
       IsTruePositive = tostring(column_ifexists("IsTruePositive_b", column_ifexists("IsTruePositive", ""))),
       ExpectedEntity = tostring(column_ifexists("ExpectedEntity_s", column_ifexists("ExpectedEntity", ""))),
       NoiseGroup = tostring(column_ifexists("NoiseGroup_s", column_ifexists("NoiseGroup", ""))),
       BenignAccount = tostring(column_ifexists("BenignAccount_s", column_ifexists("BenignAccount", ""))),
       BenignSourceIp = tostring(column_ifexists("BenignSourceIp_s", column_ifexists("BenignSourceIp", "")))
   | where IsTruePositive =~ "true" or ScenarioType has "TruePositive"
   | project
       TimeGenerated,
       ZavaCaseId,
       ScenarioType,
       IsTruePositive,
       ExpectedEntity,
       NoiseGroup,
       BenignAccount,
       BenignSourceIp,
       RawRecord = pack_all()
   | order by TimeGenerated asc
   ```

2. Query **SecurityEvent** for supporting endpoint context from the lab VM. Focus on failed logons, successful logons, special privileges, and process events around the incident timeframe. If this query is empty, confirm that the Challenge 1 Data Collection Rule association is present and that you generated fresh endpoint signals with **Generate-ZavaEndpointSignals.ps1**; do not discard the seeded true-positive incident solely because endpoint context has not ingested yet.

   ```kusto
   SecurityEvent
   | where TimeGenerated > ago(14d)
   | where Computer has "vm-zava-soc"
   | where EventID in (4624, 4625, 4672, 4688)
   | summarize
       EventCount = count(),
       FirstSeen = min(TimeGenerated),
       LastSeen = max(TimeGenerated),
       Accounts = make_set(Account, 20),
       Activity = make_set(Activity, 20)
       by Computer, EventID
   | order by LastSeen desc
   ```

3. Query **AzureActivity** for control-plane activity involving the lab VM or NSG. Focus on write operations that could expose or modify network access.

   ```kusto
   AzureActivity
   | where TimeGenerated > ago(14d)
   | where ResourceProviderValue =~ "Microsoft.Network"
       or OperationNameValue has_any ("networkSecurityGroups", "securityRules", "write")
       or Resource has_any ("nsg-zava", "vm-zava-soc")
       or _ResourceId has_any ("nsg-zava", "vm-zava-soc")
   | project
       TimeGenerated,
       OperationNameValue,
       ActivityStatusValue,
       Caller,
       CallerIpAddress,
       ResourceGroup,
       Resource,
       _ResourceId,
       Properties
   | order by TimeGenerated desc
   ```

4. Build a single timeline that combines the incident, alert, seeded, endpoint, and Azure control-plane signals. Use this as your main investigation artifact. Endpoint rows from **SecurityEvent** enrich the timeline with VM context; the seeded true-positive records plus incident, alert, and Azure activity rows provide the deterministic basis for your conclusion.

   ```kusto
   let trueRule = "ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change";
   let incidentRows =
       SecurityIncident
       | where TimeGenerated > ago(14d)
       | summarize arg_max(LastModifiedTime, *) by IncidentNumber
       | where Title has trueRule or Description has trueRule or tostring(RelatedAnalyticRuleIds) has trueRule
       | project TimeGenerated = CreatedTime, SourceTable = "SecurityIncident", Summary = strcat("Incident ", tostring(IncidentNumber), ": ", Title), Entity = tostring(IncidentNumber), Details = tostring(pack("Severity", Severity, "Status", Status));
   let alertRows =
       SecurityAlert
       | where TimeGenerated > ago(14d)
       | where AlertName == trueRule or DisplayName == trueRule
       | project TimeGenerated, SourceTable = "SecurityAlert", Summary = AlertName, Entity = CompromisedEntity, Details = tostring(pack("Severity", AlertSeverity, "Tactics", Tactics, "Techniques", Techniques, "Entities", Entities));
   let seedRows =
       ZavaSOCSeed_CL
       | where TimeGenerated > ago(14d)
       | extend
           ScenarioType = tostring(column_ifexists("ScenarioType_s", column_ifexists("ScenarioType", ""))),
           IsTruePositive = tostring(column_ifexists("IsTruePositive_b", column_ifexists("IsTruePositive", ""))),
           ExpectedEntity = tostring(column_ifexists("ExpectedEntity_s", column_ifexists("ExpectedEntity", "")))
       | where IsTruePositive =~ "true" or ScenarioType has "TruePositive"
       | project TimeGenerated, SourceTable = "ZavaSOCSeed_CL", Summary = ScenarioType, Entity = ExpectedEntity, Details = tostring(pack_all());
   let endpointRows =
       SecurityEvent
       | where TimeGenerated > ago(14d)
       | where Computer has "vm-zava-soc"
       | where EventID in (4624, 4625, 4672, 4688)
       | project TimeGenerated, SourceTable = "SecurityEvent", Summary = strcat("Windows event ", tostring(EventID), ": ", Activity), Entity = Computer, Details = tostring(pack("Account", Account, "IpAddress", IpAddress));
   let azureRows =
       AzureActivity
       | where TimeGenerated > ago(14d)
       | where ResourceProviderValue =~ "Microsoft.Network" or OperationNameValue has_any ("networkSecurityGroups", "securityRules", "write") or Resource has_any ("nsg-zava", "vm-zava-soc")
       | project TimeGenerated, SourceTable = "AzureActivity", Summary = OperationNameValue, Entity = Resource, Details = tostring(pack("Caller", Caller, "CallerIpAddress", CallerIpAddress, "Status", ActivityStatusValue));
   union incidentRows, alertRows, seedRows, endpointRows, azureRows
   | order by TimeGenerated asc
   ```

5. Rank candidate incidents by severity, recurrence, entity overlap, MITRE tactics, and asset criticality. The following query is intentionally a starting point; refine it if your data shows a stronger signal.

   ```kusto
   let LatestIncidents =
       SecurityIncident
       | where TimeGenerated > ago(14d)
       | summarize arg_max(LastModifiedTime, *) by IncidentNumber
       | where Title startswith "ZAVA-" or Title has "ZAVA" or tostring(RelatedAnalyticRuleIds) has "ZAVA";
   LatestIncidents
   | extend RuleHint = tostring(RelatedAnalyticRuleIds)
   | extend SeverityScore = case(Severity == "High", 40, Severity == "Medium", 25, Severity == "Low", 10, 0)
   | extend AssetScore = iff(Title has "VM" or Description has "VM" or tostring(AdditionalData) has "vm-zava-soc", 20, 0)
   | extend NetworkScore = iff(Title has "NSG" or Description has "NSG" or tostring(AdditionalData) has "network", 20, 0)
   | extend TruePositiveRuleScore = iff(Title has "ZAVA-TruePositive" or RuleHint has "ZAVA-TruePositive", 50, 0)
   | extend TriageScore = SeverityScore + AssetScore + NetworkScore + TruePositiveRuleScore
   | project IncidentNumber, Title, Severity, Status, FirstActivityTime, LastActivityTime, TriageScore, RuleHint, AdditionalData, IncidentUrl
   | order by TriageScore desc, LastActivityTime desc
   ```

6. Confirm the true-positive conclusion only after your evidence covers all of the following:

   1. The incident is tied to **ZAVA-TruePositive-Suspicious-VM-Access-And-NSG-Change** through **SecurityIncident** or **SecurityAlert**.
   2. The seed table **ZavaSOCSeed_CL** marks the same storyline as true positive or includes matching expected entities.
   3. The timeline includes Azure control-plane evidence from **AzureActivity** involving the VM or NSG.
   4. **SecurityEvent** provides supporting endpoint or sign-in context from the lab VM when Challenge 1 AMA/DCR ingestion and fresh helper-generated events are present.
   5. Noise-only patterns do not show the same cross-table correlation.
